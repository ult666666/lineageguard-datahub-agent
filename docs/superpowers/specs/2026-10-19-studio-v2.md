# LineageGuard Studio 2.0 — approved scope

The owner approved the architecture and delegated detailed implementation, testing and deployment-review decisions without further design check-ins. This is an AI-assisted engineering portfolio project, not an enterprise security certification or a deployed autonomous migration system.

## Outcome

Compose a typed data-change review workflow; execute actual dependent steps; inspect source-bound evidence and a separate evidence-readiness judgment; interrupt, checkpoint and resume read-only work; compare an additive alternative; run named evaluations; export inspectable artifacts. Preserve the original demo at /classic.html and existing APIs. Publish only reviewed public source and synthetic fixtures.

## Concrete implementation

Use the existing dependency-free Node foundation (Node 22.13+; Node 24 recommended), vanilla browser modules and native controls. Shared pure modules in public/studio/core are imported by both Node and browser. Separate Node modules own persistence and HTTP boundaries. No runtime npm dependencies, external fonts, analytics, paid inference or new third-party backend.

The composer compiles a bounded DAG of registered operations. It rejects duplicate nodes, cycles, missing dependencies, unknown capabilities and invalid budgets. Recipes expose sequential/parallel evidence gathering and optional precise fixture paths. The registry separates source reads, deterministic compatibility, policy and artifact generation; no step executes user code, SQL or catalog writes.

The public Studio is an explicitly labeled browser-session preview. It runs the actual orchestration interpreter against a typed synthetic-fixture tool adapter, with real step transitions, timeouts, cancellation, budgets and retries. Checkpoints remain in this browser unless exported. They are integrity-checked local state, not authenticated approvals or a durable cloud queue. The local Node service adds durable SQLite-backed checkpoints and optimistic single-run writer leases. SQLite recovery is not a distributed job scheduler. A live DataHub MCP adapter is optional, read-only, locally configured and never invoked during this build.

## Evidence and policy

A requested target must exactly match the returned target. Each evidence envelope contains kind, target, observation time, source mode/revision, completeness, and data. Missing usage is null/unknown, not zero. Partial lineage is not a complete graph. Column paths are shown only when returned as explicit paths. Risk and evidence readiness are separate. Destructive/narrowing or schema-inconsistent requests are blocked. Incomplete/stale evidence prevents favorable readiness. An acknowledgement binds exact request, recipe, evidence and policy identity; it is a local review note, never migration authorization.

The legacy MCP client is pinned to its tested 2025-11-25 handshake profile. Reject mismatched JSON-RPC IDs, error-marked tool output, unsupported negotiated versions, oversized responses and timeouts. Do not claim support for the materially different 2026-07-28 lifecycle by changing a string. Keep transport, tool and validation errors distinct and redact remote text from public HTTP failures.

## Recovery and security boundary

Checkpoint reuse requires matching request/recipe/source revision/policy, valid output digests and a valid event chain. Running/failed/cancelled nodes are not reused. Reused outputs must still satisfy freshness. A new review input invalidates old acknowledgement. Stop dispatching after cancellation; ignore late results. Checkpoint writes failing must stop progress rather than present success. Browser checksums detect accidental corruption, not a hostile same-origin actor. Imported packages are for inspection, not server authority. Local leases prevent simultaneous writers and stale writers cannot commit after takeover. No automatic migration/external side effects exist.

## Release criteria

Failing regressions before fixes. Full existing and new tests pass on Node 22/24. Real local HTTP, cancellation, restart/resume, corruption, lease-conflict, call budget and timeout tests. Real Chromium workflow, narrow screen, keyboard and stale-input tests. Named evaluation scenarios with explicit expected outcomes and policy version; no hard-coded success claims. Secret scan exact changes and static public payload. Preserve old source and screenshots. PR/CI and deployment verified against exact commit and served bytes. Do not copy runtime database, private trading source, journals, finance information or credentials to GitHub.
